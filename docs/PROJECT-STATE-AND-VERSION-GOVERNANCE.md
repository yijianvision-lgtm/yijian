## 3. 当前知识模型：保留的原则与待审计的假设

### 已有明确纲领支持的原则
- 产品核心是全部知识的过滤与个人思维框架建立；“框架是结果，过滤才是工程”。
- 认知过程：定其位 → 联其缘 → 生其相 → 归其一。
- 先定位、再关联，延伸须有依据；局部聚焦不能失去全局、谱系位置、来源路径和回归整体的能力。
- 原始资料与提取结果分开；相似不等于相同；去重不能静默覆盖原件或丢失来源。
- AI 输出是候选/提案；正式知识变更必须由用户审核确认。
- 来源、证据、决策、版本和撤销必须可追溯。

### 需要重新审视、不得擅自当作定论的模型假设
- “树/网/地图”三种表达是否足以覆盖用户真实认知结构，以及彼此如何联动。
- 单一 `parentId` 是否足以表达谱系归属；多框架 membership 如何建模。
- 四维（谱系纵向、时间、空间/世界、横向关联）与旧四向（前瞻、顾后、左顾、右盼）之间的关系。
- “四象限”是节点周边的空间交互形式，还是四类关系/定位维度的展示容器；不得把语义维度机械映射成四张固定卡片。
- XYZ 坐标、空间簇、视觉邻近不得自动生成知识关系。
- 逻辑树是过滤确认后的表达，不得让知识被强制塞进预设树形。
- 未经证据支持的关系必须标为未知/待探索，不能自动补造。

### 复核顺序
先复核知识对象与关系语义，再复核层级/框架归属，再复核四维定位，再复核空间投影，最后才调整 UI 表达。不得先用 UI 布局倒逼知识模型。

## 4. 代码与产品环境必须分开

| 区域 | 作用 | 可以证明什么 | 不能证明什么 |
|---|---|---|---|
| `archive/` | 不可变历史原型/快照 | 某个历史版本真实存在 | 不代表当前产品可用 |
| `ui-preview-*.html` | 独立 UI 试验与人工验收 | 页面源码与交互候选存在 | 不代表正式入口或后台已接入 |
| `tests/` | 自动化测试 | 测试覆盖范围内的断言通过 | 不代表真实浏览器视觉/业务验收 |
| `nebula-local.js` | 本地 IndexedDB 数据服务 | 代码/API 存在 | 不代表每条业务链端到端已验收 |
| `deepseek-worker.js` | 可选远程 AI 桥接 | Worker 源码存在 | 不代表已部署、密钥已配置或模型可调用 |
| GitHub Actions | CI / 构建检查 | 某次提交的指定检查通过 | 不代表 Pages 已部署或真实浏览器通过 |
| GitHub Pages | 静态网页发布 | 指定 commit 的页面已发布 | 不代表 Worker/数据库/AI 后台可用 |
| `index.html` | 现有正式入口 | 当前正式页面 | 不得被预览试验覆盖 |

### 能力状态统一标签
- **S0 设计中**：只有纲领/设计。
- **S1 源码存在**：有实现代码，尚未证明被页面调用。
- **S2 UI 已接入**：页面有真实调用路径。
- **S3 自动测试通过**：指定 CI/测试覆盖项通过。
- **S4 服务已部署**：对应 Pages/Worker 等服务有部署证据。
- **S5 浏览器端到端通过**：在真实浏览器完成指定流程并核实数据结果。
- **S6 用户验收通过**：用户明确认可该结果。

以上状态不可互相推导；尤其 S3 不等于 S4/S5/S6。

## 5. 变更与回滚规则（从本记录起执行）

1. 每次迭代先声明基线 commit、目标文件、允许修改范围和禁止修改范围。
2. 每一轮只解决一个可验证问题；不混合 UI 换肤、知识模型重构、后台 schema 迁移。
3. 每次提交使用独立分支或独立 commit；不覆盖历史原型。
4. 新原型使用新文件名/新版本号；历史文件只读归档。
5. 数据 schema 修改必须先有备份、迁移测试、旧数据兼容与恢复演练。
6. 所有自动生成关系/节点进入候选审核；未经用户确认不得写正式框架。
7. 交付必须附：变更文件、基线/新 commit、自动测试结果、部署结果、浏览器验收结果、未完成项、回滚 commit。
8. 若 Pages 或浏览器无法验证，明确标记“未验证”，不得把源码链接当网页预览。
9. 不改正式 `index.html`、不接正式 Worker/后台，直到用户明确批准。
10. 用户否决后先记录原因和回滚点，不以换编号方式重复错误。
