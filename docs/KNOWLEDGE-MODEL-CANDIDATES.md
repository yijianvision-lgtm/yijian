# MIND 知识模型候选方案｜第二轮：对象身份与框架位置分离

**状态：候选比较稿，不是已批准 schema。**  
**前提：** V3-A 只决定主视觉，不决定数据模型。用户已要求 E：整体重审。

## 1. 本轮需要解决的真实问题

一个知识点可能同时出现在多个知识框架里，但在不同框架中承担的逻辑角色不同。例如“书画同源”：

- 在“中国绘画史”框架中，它可能是张彦远画论体系中的一个理论命题。
- 在“中国艺术思想”框架中，它可能与文人画、书法用笔、诗书画关系共同构成思想脉络。
- 在“艺术史方法论”框架中，它可能作为一个跨时期、跨媒介的比较议题。

这不是简单把同一条树枝复制三份，也不是给节点加多个 parentId 就能解决。需要区分：
- 知识对象本身的身份；
- 这个对象在某个用户框架中的位置；
- 某个框架对它的解释、角色、排序和局部注释；
- 它与其他知识对象之间的语义关系；
- 支持该知识对象/关系的证据。

## 2. 候选 A：单一知识对象 + 多框架归属记录（推荐优先验证）

### 结构
- `KnowledgeObject`：稳定唯一身份，承载跨框架共享的核心对象。
- `Framework`：用户创建的知识框架。
- `FrameworkPlacement`：对象在某框架中的位置；包含 `frameworkId`、`knowledgeObjectId`、`parentPlacementId`、`role`、`sortOrder`、局部解释/备注。
- `RelationAssertion`：语义关系连接 KnowledgeObject；也可通过 placement 指定某个框架上下文。
- `EvidenceSpan`：支持对象、观点或关系的原始出处。

### 优点
- 同一个概念可以跨多个框架复用，不必复制核心身份。
- 同一个概念在不同框架里可以有不同父级、排序、角色和局部解释。
- 全局搜索、去重、来源汇聚更自然。
- 用户能从某框架位置跳到同一对象的其他框架位置。

### 风险/成本
- 需要处理同一对象在多个框架中存在不同定义或解释的情况；不能把所有差异压进一个 description。
- 需要明确关系是对象级通用关系，还是仅在某框架上下文中成立。
- 需要在 UI 中区分“同一知识对象”与“当前框架里的这一处位置”。

### 示例
`KnowledgeObject: K-书画同源`
- Placement P1：框架“中国绘画史”，parentPlacement=“张彦远画论”，role=“理论命题”
- Placement P2：框架“中国艺术思想”，parentPlacement=“中国艺术观念”，role=“核心思想”
- Placement P3：框架“艺术史方法论”，parentPlacement=“跨媒介关系”，role=“比较议题”

三处共享同一个知识对象 ID，但有不同路径。用户从 P1 点击“查看其他框架位置”可到 P2/P3。

## 3. 候选 B：框架上下文节点 + 共享概念引用

### 结构
- 每个框架拥有自己的 `FrameworkNode`，位置、解释、层级完全局部化。
- 多个 FrameworkNode 可引用同一个 `CanonicalConcept`。
- 关系可以连接框架节点，也可以连接 canonical concept。

### 优点
- 每个框架中的知识路径和解释完全独立。
- 更适合一个概念在不同学科中发生明显语义变形、定义差异或教学侧重点不同的情况。
- 框架局部的排序、证据、注释、版本容易表达。

### 风险/成本
- 搜索、去重、跨框架汇总更复杂。
- 用户容易误以为两个 FrameworkNode 是两个不同概念，或反过来误把不同语境强行合并。
- 同一关系在不同框架上下文中可能重复维护。
- 需要清楚显示“同一概念的不同框架实例”。

## 4. 候选比较

| 比较维度 | 候选 A：对象 + Placement | 候选 B：上下文节点 + Canonical |
|---|---|---|
| 核心身份 | 全局单一 | 概念身份与框架节点分层 |
| 多框架不同父级 | 通过 Placement 表达 | 通过不同 FrameworkNode 表达 |
| 不同框架局部解释 | Placement 注释或 Claim | FrameworkNode 局部字段 |
| 跨框架搜索/去重 | 较直接 | 需跨实例聚合 |
| 关系表达 | 对象级 + 上下文级 | 概念级 + 节点实例级 |
| 版本复杂度 | 对象版本与 Placement 版本分开 | Canonical 与 FrameworkNode 双层版本 |
| 适合场景 | 同一知识对象在多个框架中复用 | 同一概念在各框架中有显著不同语境 |
| 主要风险 | 全局对象定义过度统一 | 实例膨胀与重复维护 |

## 5. 当前建议：混合模型

建议先用 A 做基础身份模型，同时吸收 B 的上下文解释能力：

1. `KnowledgeObject` 保持稳定身份，不塞入单一框架 parent。
2. `FrameworkPlacement` 负责每个框架里的父子关系、角色、排序、局部说明。
3. `KnowledgeClaim` 负责对象上的具体定义、观点、主张，允许并存、比较、争议，不用单个 description 覆盖所有观点。
4. `RelationAssertion` 负责有类型的关系；必要时附着于 Placement 上下文。
5. `EvidenceSpan` 可以支持对象、Claim 或 RelationAssertion。
6. 原始 SourceAsset 永远独立保存；多个 EvidenceSpan 可以指向同一个原始文件。

这是设计建议，不是数据库实施决定。

## 6. 用真实案例验证模型

### 案例一：同一对象跨框架
“书画同源”同时进入“中国绘画史”和“中国艺术思想”。验证两个框架可以有不同父级路径，但共享对象身份。

### 案例二：多个观点并存
同一个命题在不同文献中有不同解释。系统应保留 Claim A、Claim B、来源和争议，而不是覆盖成一个统一摘要。

### 案例三：同一结论多来源
PDF 第 12 页、Word 第 4 节、EMMX 某分支都支持同一主张。系统汇聚证据，但每个来源位置保持独立。

### 案例四：关系有争议
用户认为 A 导致 B，另一来源只证明两者同时出现。系统要能保存“用户提出的因果假设”和“来源仅支持共现”这两种不同状态，不能直接把它标为事实因果。

### 案例五：合并与拆分可逆
两个相似节点可能实际指不同概念；合并前显示差异和来源，合并后可恢复两者的独立身份、证据、学习记录、空间位置和关系。

### 案例六：空间位置不代表语义
两个节点在 3D 场景中相邻，但无关系记录。系统不得自动把它们连成“相关”；反之，语义上有关联的节点也可在空间中相距很远。

## 7. 对 V3-A UI 的影响

V3-A 仍然作为纯宇宙画布方向，不需要因模型重审而推翻视觉选择。但交互必须能区分：
- 当前星点对应的 KnowledgeObject；
- 当前知识框架中的 Placement；
- 当前聚焦的 Claim/观点；
- 当前打开的证据；
- 当前显示的语义关系；
- 当前镜头下的空间投影。

用户点击同一对象的不同框架入口时，镜头可以聚焦同一个知识身份，但侧边上下文路径、局部关系和解释会切换。空间位置是否跨框架共享，需要后续单独决策，不能默认。

## 8. 本轮不做的事情

- 不新增 IndexedDB store。
- 不修改 `parentId`。
- 不迁移现有 graph。
- 不改正式入口或预览页。
- 不执行真实数据合并/拆分。
- 不将此候选直接写成已批准架构。

下一轮应先让这两种模型通过真实知识案例逐项测试，再确定概念边界，最后才设计 schema migration。
