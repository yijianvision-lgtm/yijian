# MIND 知识模型复核｜第一轮：拆开概念，不先定数据库

**日期：2026-11-08**  
**状态：模型审计草案，未批准实施。**  
**关联基线：** V3-A 为当前视觉方向；知识模型整体重审，旧 schema 暂停作为设计依据。

## 0. 本轮结论

此前项目把四类不同事物放在同一个“知识图谱/四维/四象限”词汇下面，导致数据模型、交互布局和哲学纲领互相替代。本轮先拆开：

- 知识是什么（对象）。
- 知识凭什么成立（来源与证据）。
- 知识与知识之间是什么关系（语义关系）。
- 知识在用户框架里处于什么位置（谱系/归属）。
- 知识如何随时间变化（知识时间）。
- 用户如何在三维场景里看到它（空间投影）。
- 用户如何学习、修正自己的理解（学习与认知历程）。

这些维度可以关联，但不能合并成同一个字段，也不能用视觉坐标推断语义。

## 2. 当前概念分层（审计建议，不是最终定案）

| 层 | 核心问题 | 应表达的内容 | 不得偷换成 |
|---|---|---|---|
| 知识对象 | 这个东西是什么？ | 概念、命题、方法、事件、人物/作品、问题、观点等 | 页面节点外观 |
| 来源/证据 | 我凭什么这样说？ | 原始文件、段落、页码、导图路径、引用、证据强度 | AI 摘要或知识关系 |
| 语义关系 | 它与别的知识是什么关系？ | 因果、组成、对比、支持、反驳、实例化、演化等 | 线条连接或空间邻近 |
| 框架归属 | 它在我的知识框架哪里？ | 一个或多个框架中的明确角色、路径、层级 | 所有关系都塞进 parentId |
| 时间 | 它何时成立/发生/演变？ | 事件时间、理论有效期、版本时间、学习时间 | 节点在屏幕上的前后 |
| 空间投影 | 用户如何在宇宙里观察？ | XYZ 坐标、缩放、聚类、镜头、布局锚点 | 知识的真实语义 |
| 认知历程 | 用户如何理解和掌握？ | 用户解释、学习记录、错误、修订、复习和应用 | 知识本体自身的历史 |

## 3. 必须保留的纲领原则（高优先级）

1. **定位优先**：用户必须知道当前对象、上下文、所属框架、路径和全局位置。
2. **关联有类型、有方向、有依据**：不能只有无语义的线。
3. **生长有依据**：新增知识和关系必须可追溯来源，AI 生成只是候选。
4. **局部可回全局**：任何深入操作都能恢复进入前的上下文。
5. **原始资料不可被摘要覆盖**：文件、原文、提取结果、人工修订分别保留。
6. **相似不等于相同**：重复检测先提出候选，保留来源和差异；合并必须可撤销。
7. **人工审核优先**：AI 不能静默创建正式关系、覆盖节点、改变框架位置。
8. **多源汇聚不丢出处**：同一知识对象可关联多个来源，来源之间不互相覆盖。
9. **用户私人资料私有**：导入的私人讲义及提取内容默认仅本人可访问；不可搜索或被其他用户查看。
10. **稳定身份与版本**：对象 ID 不随名称、布局或框架路径改变；所有重要改动有版本与回滚记录。

## 4. 旧模型假设审计表

| 旧假设/实现 | 风险 | 本轮处理 |
|---|---|---|
| 一个知识点只有一个 `parentId` | 无法表达多框架归属、概念的多种上下文 | 暂停作为最终模型；先区分主谱系与框架 membership |
| `frameworkId` 是节点唯一归属 | 与多框架复用冲突 | 需要明确 membership / contextual placement 结构 |
| 四个固定象限就是四种关系 | 象限是呈现方式，不等于关系全集 | 作为聚焦 UI 候选；关系类型独立建模 |
| 早期前瞻/顾后/左顾/右盼等于谱系/时间/空间/横向四维 | 两套语义来源不同 | 禁止直接映射；保留为早期思考提示的历史语义 |
| XYZ 坐标代表知识关系 | 空间布局可能误导语义 | 坐标仅为可视化投影；不可据此自动建边 |
| 时间最近的节点就是时间关联 | 时间接近不等于因果或相关 | 时间字段和时间关系需显式、带类型和证据 |
| 树/网/地图就是完整认知本体 | 表达方式限制知识模型 | 暂定为不同视图，不是本体定义 |
| AI 可以自动补足关系 | 容易制造虚假关联 | AI 只能生成待审核提案 |
| 自动去重等于删除重复节点 | 可能损失来源、差异和独立语境 | 只产生重复候选；合并要可撤销且保留别名与来源 |

## 5. 需要定义的核心实体（仅概念层，不是 schema）

- **KnowledgeObject**：稳定身份的知识对象。
- **SourceAsset**：用户原始文件/资料，保持原件不变。
- **EvidenceSpan**：来源中的具体证据位置，如页码、段落、导图节点。
- **KnowledgeClaim**：关于知识对象的具体陈述/命题，避免把不同观点压成一个“定义”。
- **RelationAssertion**：两个或多个对象之间的有类型关系，含方向、提出者、依据、状态和有效时间。
- **Framework**：用户建立的知识框架。
- **FrameworkMembership / Placement**：知识对象在某框架中的归属和上下文位置；允许待验证是否一对多。
- **KnowledgeVersion**：对象或关系的版本记录。
- **ReviewProposal**：AI 或用户提出的新增/修改/合并/拆分/关系提案。
- **SpatialProjection**：场景坐标、布局策略、锁定位置；与语义对象分离。
- **LearningRecord**：用户在某时刻对某对象的理解、回答、掌握与复习记录。

这些是概念边界建议，不可直接据此迁移现有 IndexedDB/数据库。

## 6. 关键关系需要区分

至少不要把下列关系全部压成一个 `links[]`：
- 谱系：属于、上位概念、下位概念、组成部分、实例。
- 论证：支持、反驳、证据支持、引用、推导。
- 语义：相似、对比、互补、冲突、同义/近义。
- 因果/机制：导致、促进、抑制、依赖、机制解释。
- 时序：先于、后于、同时期、演化自、替代。
- 来源：源自、摘录自、解释自、被某证据支持。
- 应用：应用于、实例化为、案例说明。
每条关系必须区分“已确认”“待审核”“被否决”“已撤销”，并保留提出者与证据。

## 7. 当前尚未决策的问题

1. 一个知识对象能否同时进入多个用户框架？初步建议可以，但要区分对象身份与框架中的上下文解释。
2. 框架是否只有一条主谱系路径？可能需要用户显式指定“主要路径”，同时允许其他 membership。
3. 四维定位是每个对象的必填字段，还是按需投影？不宜强迫所有对象都填满四个维度。
4. 四象限是否继续作为主交互？可以保留为 V3-A 聚焦后的一个可展开视图，但不能等同完整关系模型。
5. “空间/世界”是知识领域、物理地理空间、系统边界，还是多种空间语义的集合？必须拆分。
6. 时间至少区分事件时间、知识有效时间、资料发表时间、用户学习时间和系统记录时间。
7. 一个对象可能有多个互相竞争的定义/观点，需不需要 claim/statement 层？建议需要，避免单字段描述覆盖争议。
8. 树状逻辑究竟是系统主结构，还是用户确认后生成的一个视图？需根据用户真实使用方式再定。
9. 关系是否必须有证据？部分关系可为用户显式建立，但需标明来源为用户判断，不能假装文献证实。
10. 3D 空间是否需要自动布局？自动布局只能给建议；用户可固定位置，布局不能改变语义关系。

## 9. 验收底线

- 不因视觉位置自动产生语义关系。
- 不因文本相似自动合并正式知识。
- 不丢失原始文件、出处、证据和差异。
- 不把 AI 推断标成事实。
- 不强迫每个节点填满四象限。
- 不把单一 parentId 当成万能归属。
- 不将用户学习时间混入知识事件时间。
- 任何正式修改可追溯、可比较、可撤销。


## 10. 当前真实代码的后台审计（main 读取，只读检查）

### 本地数据层现状
- `nebula-local.js` 声明 `DB_NAME = nebula_local_v2`、`DB_VERSION = 5`，包含 22 个 IndexedDB stores。
- 数据层文件头明确写明：无登录、无云数据库、无账户服务、无远程文件存储；知识和原始资料保存在当前浏览器 IndexedDB。
- 这与此前产品要求的“个人账户私有、跨设备访问”存在明确缺口。当前 local-first 只能证明单浏览器本地保存；不能宣称已具备账户私有云同步。可继续保留 local-first，但跨设备同步需要独立的身份、加密/访问控制、同步冲突与恢复设计，尚不能假设已实现。
- DeepSeek 对话支持用户导出 JSON/TXT 后导入、解析与保留原始导出；没有证据证明已自动同步 DeepSeek 网页版新对话。不得宣称实时同步。

### 当前框架归属结构
- 图谱节点仍以 `parentId` 组织一条父子路径。
- Framework 记录保存 `rootNodeIds`，`getFrameworkTree` 从全局 graph 节点按 `parentId` 递归构树。
- 没有独立的 FrameworkMembership / ContextualPlacement store。
- 同一节点可被不同框架 rootNodeIds 引用的可能性存在，但无法在不同框架中为同一知识对象保存不同的上下文父级/路径/角色。
- 因此“多框架 membership”尚未被充分建模；不能把当前结构说成已经完整支持一个知识对象在多个知识体系中的不同位置。

### 四维空间投影的真实程度
- `getSpatialProjection` 返回固定的 `["lineage","time","space","horizontal"]`。
- 默认语义坐标由树深度/parentId、`knowledgeTime/date`、`domain/domainPath` 推导；布局坐标由保存位置或节点的 x/y/z 得到。
- 这属于现有投影机制，不代表四个维度都有独立、完整、带证据的关系模型。尤其 space 默认更接近 domain 标签，不能把“领域”与物理地理空间或现实世界空间混为一谈。

### 关系与审核
- `knowledgeRelations` 是独立 store，关系两端节点会校验存在；但 `saveKnowledgeRelation` 主要验证端点，并未统一强制关系类型枚举、方向约束或证据要求。
- `relationEvidence` 有 proposed/confirmed/disputed/unknown 状态，这比普通无类型连线更好，但需要统一到所有关系写入路径。
- AI 关系提案能先存入 Review Proposal，用户接受后再写入关系；这是应该保留的安全原则。
- 正式知识和 AI 提案目前有审核边界，但需要检查每条写入路径，不能只依据一两个测试断言宣布整个系统安全。

### 版本与合并/拆分风险
- `saveNodeVersion` 的“是否发生变化”比较字段目前只包括 name/coreWord/desc/before/after/left/right/parentId/status/confidence；诸如 knowledgeTime、domain、framework context 等字段变化可能不触发新版本。需扩大字段快照比较或采用规范化完整快照哈希。
- merge 实现会重映射部分父级、图谱 links、nodeSourceLinks 和 knowledgeRelations，但当前实现没有同步迁移所有引用该节点的 store（例如 learningRecords、nodePositions 等需要逐项检查）。被合并节点删除后可能留下悬空引用。
- split 实现主要替换图谱节点并创建版本；目前测试只确认拆分后节点存在，没有验证原始来源、关系证据、学习记录、空间位置、筛选决策是否按用户确认的映射迁移。
- runtime tests 对 merge 的检查目前主要是来源链接、子节点 parentId、关系存在；对 split 的检查较浅。不能把“merge/split 测试通过”理解成所有关联数据都完整保留。
- 在补齐引用迁移和恢复测试之前，不应对重要真实知识批量执行 merge/split。每次先做完整备份，并在副本数据上演练。

## 11. 当前应该保留、暂停和不应再做的东西

### 保留
- IndexedDB local-first 作为当前本地原型的数据存储层。
- 原始文件与提取候选分离、保留原件。
- Extraction → Filter → 用户审核 → 正式图谱的流程。
- 来源证据定位、关系证据、提案审核、版本记录、完整备份/恢复。
- 真实知识数据与演示数据隔离；没有数据时显示真实空状态。
- 语义关系与空间投影分开，空间坐标不创建知识边。

### 暂停，待模型审定
- 单一 parentId 作为全系统唯一归属。
- 固定四维数组作为所有知识对象的必填维度。
- 将 domain 当成完整的 space/world 维度。
- 以树为唯一主结构或把树/网/地图直接定成最终本体。
- 自动布局对语义坐标的解释。
- 批量自动去重、自动合并、自动补关系。
- 正式账号/跨设备同步方案和 Worker 部署。

### 不要再做
- 不得让随机坐标、距离、最近年份或同领域标签自动产生语义关系。
- 不得将 AI 推断直接写成已确认知识。
- 不得删除原始资料、重复来源或不同语境。
- 不得把已撤回的 V7/V9 重新当成当前设计候选。
- 不得因 CI 红灯而恢复用户已撤回的实验页面。
- 不得只为让测试变绿而删除运行测试或降低验收标准。
- 不得把 Pages 发布成功说成后台已上线。
- 不得改正式入口或数据库 schema，直到模型与迁移计划得到用户确认。

## 12. 下一轮技术工作（先测试后重构）

1. 建立引用完整性测试：merge/split/delete 后检查 graph、relations、relationEvidence、nodeSourceLinks、learningRecords、nodePositions、filterDecisions、frameworkVersions 等是否有悬空引用。
2. 完整快照版本测试：每个会影响知识语义、归属、来源或关系的字段变更都必须形成版本。
3. 多框架测试：同一知识对象在不同框架中拥有不同上下文路径，验证当前模型缺口。
4. 关系 schema 测试：类型枚举、方向、状态、证据和用户/AI 提出者统一校验。
5. 本地备份恢复测试：覆盖所有 store、二进制原件、来源链接和版本，并验证校验失败时不会覆盖现有数据。
6. 用户私有多设备同步先做威胁模型和冲突方案，不直接引入远程存储。
7. 真实浏览器测试 V3-A；不以静态字符串测试替代实际交互。
